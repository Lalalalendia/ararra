# РидЭра RE-06 — управляемая суточная квота Gemini (первый инкремент)

## Основание и фактический контракт

Google Gemini API считает rate limits **по Google Cloud проекту**, а
НЕ по API-ключу; отдельные ключи одного проекта не дают дополнительных
лимитов. Квота привязана к модели и классу доступа. Действующие значения
проверять в Google AI Studio, не угадывать. Лимит условно 21 RPD — лишь
пример. При наблюдении 21/20 фактическое ограничение может быть 20:
защитный cap следует ставить **ниже или равным** реальной разрешённой квоте.

RPD = `requests per day`; также существуют `requests per minute` (RPM),
`input tokens per minute` (TPM) и другие ограничения/платные расходы.
Размер исходного текста не «весит часть одного запроса» в RPD: запрос
`generateContent` считается одним вызовом независимо от размера, но
его **токены ограничиваются и учитываются отдельно**. Контроль размеров
и токенов — самостоятельный этап, НЕ реализованный этой миграцией.

Официально RPD обновляется в **00:00 America/Los_Angeles**
(PST/PDT, с DST). Интервал не равен «24 часа с первого запроса» и
не зависит от локального времени сервера.

Источники: [Gemini rate limits](https://ai.google.dev/gemini-api/docs/rate-limits),
[Gemini token counting](https://ai.google.dev/gemini-api/docs/tokens),
[Google AI Studio usage/rate limits](https://aistudio.google.com/).

## Настройка worker и read-only API

```ini
CHAPTERA_GEMINI_MODEL=gemini-3.8-flash
CHAPTERA_GEMINI_QUOTA_PROJECT=my-real-google-project
CHAPTERA_GEMINI_REQUESTS_PER_DAY=21
```

Оба параметра обязательны для включённого ограничения. `0` —
существующее **отключённое** поведение (явный opt-in). Это локальный
защитный cap, а не подтверждение лимитов AI Studio и не разрешение
производить платные вызовы. Использовать один и тот же ID проекта для
всех ключей этого Google-проекта; нельзя разбивать один проект по
псевдонимам, чтобы имитировать дополнительные квоты.

Никакие значения API-ключа, промпта, перевода или тела 429 не сохраняются
в ledger. Квоты `(project, model, Pacific-day)` в одном SQLite:
`gemini_daily_requests` с `used` и `externally_blocked`.
Транзакционный `BEGIN IMMEDIATE` предотвращает гонку резервирования.
Резервирование происходит **до сетевого вызова**; если статус неизвестен
из-за таймаута, резерв НЕ возвращается для защиты от двойного расхода.

## Как ведёт себя очередь

1. Каждый `GeminiProvider.generate` проходит через один
   `QuotaControlledProvider`: предварительный контекст, основной
   перевод, атомные пакеты, repair и повторы. Вся цепочка —
   **несколько запросов**, не одна глава = один запрос.
2. Если разрешённый RPD локально исчерпан, запрос вообще не уходит
   в Google. Задание переводится в `retry_wait`, `run_after` —
   ближайшая следующая полночь Pacific. Повтор не сжигает конечный
   `max_attempts`; уже принятые версии не меняются.
3. Если Google вернул структурированный `429` с `quotaId=...PerDay...`
   (например RPD или TPD), все локальные обращения той же модели
   проекта блокируются до следующей Pacific-полуночи — даже если
   наша программа насчитала меньше 21.
4. **Неизвестный** 429 / RPM / TPM / spend limit остаётся обычным
   transient 429 с ограниченным exponential backoff: нельзя без
   оснований интерпретировать его как истекшую суточную квоту.
5. Один worker и одна SQLite база остаются обязательной предпосылкой
   корректной очереди. Другая программа с тем же Google-проектом
   может расходовать внешнюю квоту; наш ledger не видит её вызовы
   и корректирует поведение только после явного ответа `PerDay`.
6. Если один длинный job получил **успешные** ответы на часть
   subrequests до упора в квоту, сохранённых **субзапросов** пока нет:
   после сброса он повторит весь preflight. Только после более чем
   двух таких дорогих частичных пауз job завершается **failed** с
   рекомендацией разбить задачу или реализовать per-packet checkpoints.
   Сами по себе отклонённые ответы Google `429/PerDay` не являются
   успешной частичной работой и не расходуют этот лимит: задача остаётся
   в `retry_wait` для следующих суток.

Отображение quota в UI, пакетный выбор глав, локальное RPM/TPM,
планирование по реальному `countTokens`, расходы по токенам и
поштучные checkpoints после каждого atom-пакета **не входят**
в этот PR; выполняются отдельными инкрементами RE-06.

## Приёмка (offline, без Gemini и оплаты)

- 21 успешная конкурентная резервация в SQLite, 22-я локально запрещена.
- Все ключи одного проекта и одной модели видят один счётчик, в т.ч.
  после создания второго `QueueStore` на той же SQLite.
- Разные модели/проекты имеют отдельные записи.
- Переход в следующий день с учётом **23/25-часовых** DST-дней.
- Worker с `max_attempts=1` после исчерпания RPD не теряет
  ожидающую главу, новый день позволяет перевести её.
- Реальная ежедневная ошибка 429 по quotaId блокирует проект,
  RPM-429 не принимается за дневную.
- Защита от бесконечного перерасхода при невосстановимом
  длинном задании, конфиденциальность ошибок и ключей.
- Python 3.11/3.12, архитектура, Node/Jinja, настоящий Chromium.

**Не запускать автоматический платный тест, пока не пройдены
RE-01 VPS/HTTPS и добровольное подтверждение бюджета.**


## RE-06B-QUOTA-READ-01: безопасное отображение дневной квоты

**Раздельные процессы:** для отображения статуса API должен получить
те же три несекретных параметра `CHAPTERA_GEMINI_MODEL`,
`CHAPTERA_GEMINI_QUOTA_PROJECT` и `CHAPTERA_GEMINI_REQUESTS_PER_DAY`,
что и worker, и использовать ту же SQLite-базу. `CHAPTERA_GEMINI_API_KEY`
для чтения квоты в API **не нужен** и не должен туда передаваться.
Если параметры настроены только у worker, API честно вернёт
`enabled=false`, даже если worker ведёт дневной счётчик.
Не запрашивать и не угадывать project ID по содержимому базы.


- `GET /v1/quota/gemini` требует аутентификацию участника команды и не вызывает Gemini. Ответ не содержит идентификатор Google-проекта или секреты.
- `enabled=false` означает, что локальный лимит не настроен. Это **не** утверждение о безлимитном тарифе.
- При `enabled=true` API сообщает модель, день Pacific, зарезервированные попытки (`used`), защитный cap (`limit`), локальный остаток (`remaining`), момент следующей Pacific-полуночи (`reset_at`) и флаг `externally_blocked`.
- Чтение не резервирует запросы и не создаёт таблицу ledger, если worker ещё ни разу не работал.
- Вкладка «Очередь переводов» показывает остаток и локальное время сброса. Учёт охватывает только запросы, которые проходили через **эту SQLite-базу**, а не весь расход Google-проекта.
- Это счётчик попыток, а не оплаченных токенов. RPM/TPM, токенизация и фактические расходы остаются отдельными задачами RE-06B.
