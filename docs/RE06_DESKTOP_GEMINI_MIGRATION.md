# RE-06: перенос Gemini scheduler из full_cycle_app

Источник — настольная программа `full_cycle_app`, переданная владельцем.
Рабочая конфигурация: один Gemini API-ключ одного Google-проекта; перенос
не вводит мультиключевую схему и не переписывает рабочие алгоритмы.

## Что перенесено
- `src/chaptera_server/gemini_scheduler.py`: исходные 588 строк
  `full_cycle_app/translation/gemini/api/request_scheduler.py` без изменения
  алгоритмов. Адаптирован только import `OperationCancelledError`.
  SHA-256 исходника (без завершающего LF):
  `8fc1b4c2293b08a9911424ff0b0bdeda714cb3531445cbe7a041ff1e72cc24f5`.
  Тест проверяет точность переноса.
- `ScheduledGeminiProvider`: прослойка вокруг имеющегося серверного
  Gemini/SQLite RPD. Порядок допуска:
  desktop RPM/RPS/TPM -> desktop network controller/circuit ->
  atomic SQLite RPD -> HTTP Gemini. Отказ до HTTP не тратит RPD.
- Роли `translation`, `targeted_repair`, `glossary` и cancellation
  поступают из единого TranslationCore и контекстного preflight.
- Для временного HTTP 429 — desktop cooldown и уменьшение RPM на 25%;
  5xx и сетевые ошибки отслеживаются circuit breaker. Суточный 429
  по-прежнему обрабатывает прежняя постоянная SQLite-квота.
- Настольные настройки текущей модели: RPM 5, TPM 250000, верхняя
  граница output 65536; реальное `maxOutputTokens` ограничено 98%,
  как в настольном Gemini handler. Проверяются до сетевого запроса.

## Следующие завершённые блоки

- **PR #38 — атомные контрольные точки:** уже проверенные исходным
  desktop `CoverageMap` пакеты, включая targeted repair, сохраняются
  в SQLite с lease fencing и ключом точного prompt/payload/role/model.
  Срабатывает восстановление после паузы и перезапуска без повторного
  вызова Gemini. Не переносит ещё streaming или контекстные окна.
- **PR #39 — классификация и отложенные повторы:** из
  `full_cycle_app/.../worker_helpers/error_analyzer.py` без изменения
  взят метод `_classify_exception` с приоритетом условий (включая
  provider unavailable перед network). Серверный
  `gemini_error_bridge.py` только превращает очищенные HTTP-коды в
  существующие `ErrorType` через оригинальные классы исключений.
  `TemporaryRateLimitError` (429/RPM), `ProviderUnavailableError`
  (5xx) и `NetworkError` не расходуют конечные `max_attempts`.
  Постоянный `transient_streak` наращивает паузу до 300 секунд,
  `Retry-After` учитывается до 3600 секунд. 401/404/400
  блокируют обработку новых задач в текущем worker, как desktop
  `ABORT_WORKER`; текущая плохая глава получает явную ошибку.
  Дневная квота по-прежнему идёт через RPD и ждёт Pacific reset.
  Непонятные/искажённые 200/200 MAX_TOKENS не объявляются «сетью»:
  пока доступны только **ограниченные countable повторы**, не
  полноценный partial salvage. Полезная работа не перечёркивается
  при временном отказе; сохранённые атомы из PR #38 остаются доступны.

## Что ещё НЕ перенесено

Полный desktop `ErrorAnalyzer.analyze_and_act` включает действия
`split_v2`, `coverage_v2`, `translation_debts`, `finalize_only`,
сессионный model failover, streaming salvage и обработку нескольких
типов ошибок в рамках общего history. Это **не** заявляется
реализованным: GUI и настольная очередь имеют другую
инфраструктурную оболочку, и их не нужно вслепую копировать
в серверную SQLite. Далее переносим **то же поведение** в серверные
порты с мокированными desktop traces и crash-test.

Scheduler настольной программы хранит RPM/TPM/circuit в памяти процесса,
поэтому при рестарте эти минутные окна сбрасываются. Устойчивое суточное
RPD в облаке **не** сбрасывается: оно остаётся в SQLite. Поддерживается
один worker/key по умолчанию. Не заявляется межпроцессная точность RPM
или полное покрытие тарифов.

Нет вызовов платного Gemini и нет VPS deployment.

## RE-06 — контрольные точки окон контекста (следующий инкремент)

Настольные правила создания контекста и существующие серверные
`source_windows`, `_decode_context`, `validate_context_response` и
`_ground_entities` **не меняются**. Сохраняется уже валидированный JSON
каждого окна в **том же** SQLite checkpoint-порту из PR #38. Никаких
новых планировщиков или альтернативных переводчиков не вводится.

Ключ окна включает точный prompt и scope: весь исходный `source_hash`,
`chapter_revision`, `glossary_hash`/`glossary_revision`, зависимости
предыдущей главы, индекс окна, границы, hash фрагмента, книгу и главу.
Дополнительную изоляцию по Gemini-модели обеспечивает уже существующий
`SQLiteAtomCheckpoint`. Поэтому нельзя смешать старый исходник,
соседние главы и несовместимые модели. Восстановленный JSON **повторно**
проходит полный валидатор и проверку принадлежности фактов конкретному окну;
неизвестные или повреждённые данные закрываются ошибкой, а не
подставляются в перевод.

Каждый подтверждённый ответ фиксируется на диске **после** валидации,
до вызова Gemini для следующего окна. При суточном лимите **один запрос**
на следующий день продолжается следующее окно, без повторной генерации
готовых. Когда сборка главы завершена, лишний приватный checkpoint-текст
удаляется транзакционно существующей логикой очереди; проверенный
агрегированный context snapshot остаётся в библиотеке.

Учёт частичных дорогих запросов в worker вычитает каждый сохранённый
контекстный ответ **ровно один раз**, чтобы новая защитная граница не
ошибочно отключила счётчик действительно потерянных результатов
трансляции. На этом этапе не заявлен salvage внутри недополученного
HTTP/streaming-ответа: только завершённые и проверенные окна.

Офлайн-проверки: два окна, суточный лимит 1 RPD, три дня с перезапуском
worker/SQLite, ложная ошибка второго окна и продолжение первого,
семантическая подмена cached JSON с пересчитанным SHA и отсутствие
обхода исходных revision fences.

## RE-06 — первый безопасный partial-answer salvage (PR #42)

В настольном `GeminiApiHandler` `MAX_TOKENS` с непустым ответом
передаётся через оригинальный `PartialGenerationError`. Серверный
`GeminiProvider` раньше отбрасывал весь текст, после переноса передаёт
его **тем же уже общим классом исключения**, без новых API-key, планировщиков
или альтернативного переводчика.

Для `atoms_v1` минимальный синтаксический адаптер извлекает только
**полностью законченные JSON-объекты `segments`** из оборванного ответа.
Все сегменты проходят штатный, ранее перенесённый desktop
`reconcile_coverage_response`, после чего валидированная часть
сохраняется прежним SQLite lease-fenced checkpoint. Повторные запросы
`targeted_repair` адресуются только незакрытым исходным render-domain
через имеющиеся `translation_debts`/CoverageMap, без генерации заново
доказанной части. Неизвестные/перекрывающиеся атомы, незаконченный
JSON-string и safety stop **не** сохраняются, даже если response был
частично получен. При quota reset/restart проверенные атомы читаются из
SQLite и повторно валидируются.

В `html_v0` непроверенный partial text не публикуется. Физический
сетевой обрыв без доказанных атомов остаётся настольным
`NETWORK` с non-countable retry; `MAX_TOKENS` без пригодной части —
ограниченный retry, не бесконечная смена ключей.

**Граница:** это перенос ответа `MAX_TOKENS` по существующему
`generateContent` HTTP-контракту. **Обработка физически оборванного
HTTP/SSE тела на сервере и полноценный desktop `split_v2`/
`finalize_only` остаются отдельными задачами.** Не называть этот
этап полным streaming recovery.

Проверки: real `httpx.MockTransport` для `MAX_TOKENS`, thought
filtering, проверенный частичный JSON при трех atom-domains,
`targeted_repair` только двух недостающих, поддельный atom ID —
fail-closed, RPD=1/сутки и перезапуск со сохранённым результатом.

## RE-06 — реально оборванный поток Gemini SSE (экспериментальный opt-in)

Для `atoms_v1` серверный `GeminiProvider` может использовать
`streamGenerateContent?alt=sse` вместо обычного `generateContent`,
если **явно** выставлено `CHAPTERA_GEMINI_STREAM_ATOMS=1`.
Значение по умолчанию `0`: существующий REST-контракт
`html_v0` и рабочие non-stream вызовы не меняются.

В основе — принцип настольного обработчика `full_cycle_app`:
инкрементально собирать только `content.parts[].text` без
`thought=true`, фиксировать `finishReason` и возвращать
**оригинальный `PartialGenerationError`** с уже полученным
ответом при физическом обрыве/недополученном STOP/MAX_TOKENS.
Сетевой сбой до получения текста остаётся `NetworkError`-
совместимой временной ошибкой. `SAFETY`/policy stop и
неизвестные статусы не проходят partial salvage.

Собранный незавершённый поток передаётся в **PR #42**
`salvage_partial_atom_response`, который пропускает только полностью
декодированные сегменты, и далее **прежнему** `CoverageMap`,
SQLite checkpoint и `targeted_repair`. Никакого
второго алгоритма перевода, локального бюджетного менеджера
или управления множеством ключей не создаётся.

Предусмотрены ограничения на размер кадра/ответа, текст не
записывается в журналы и ошибки, исходные токены prompt и
API-ключ сохраняются только в защищённом HTTP client.
Валидированный SSE `STOP` публикуется исключительно после всех
штатных QA-проверок главы.

Испытания offline через реальный `httpx.MockTransport`:
SSE чанки через разные TCP-sized фрагменты, thought filtering,
токены usageMetadata, обрыв после partial text, обрыв до
первого ответа, MAX_TOKENS, SAFETY stop и сквозное
восстановление через существующий атомный `targeted_repair`.
**Платный API, внешние запросы и VPS deployment не запускались.**

Ограничение: этот перенос не покрывает все разновидности
desktop `translation_debts`/`split_v2`/`finalize_only`
и автоматически не включает SSE на продакшене.

## RE-06 — долговременные долги и строго локальная финализация (PR #44)

Продолжаем **настольную семантику** `translation_debts` и
`finalize_only`, не создавая отдельный переводчик:
`repair_domains`, `CoverageMap`, `apply_proven_repair` и
`build_render_plan` остаются исходными ядром desktop, а результаты
все ещё хранятся в том же lease-fenced `atom_job_checkpoints`.

В SQLite добавлена минимальная **не содержащая текст** таблица
`atom_recovery_state`: `job_id`, точная модель и source SHA,
`debt_repair/finalize_only`, число незавершённых source-owned
доменов и отдельные ограниченные счётчики. Это metadata checkpoint
в рамках существующего job, **не второй очередь**, не выделенный
API-key и не повторная реализация `translation_debts`.

Если повреждены более 12 доменов, worker больше не отказывает
сразу: он исправляет **не более 12 НОВЫХ** доменов за один claim,
сохраняя каждый подтверждённый ответ; потом родительская задача
переходит в `retry_wait`/desktop-style `debt_wait` без расхода
обычных `max_attempts`. На новом lease прежние 12 Proof/SQLite
воспроизводятся локально, Gemini вызывается только для оставшихся.
Одновременно действуют старые Pacific-day RPD, RPM/TPM и circuit
breaker. Без SQLite checkpoint автономный TranslationCore
сохраняет старый fail-closed предел и не производит 13+ сетевых
repair вызовов без гарантии сохранности. Максимум 32 debt waves
ограничивает цикл зависания.

После доказанного полного `CoverageMap` и `build_render_plan`
до локальной сборки записывается `finalize_only`. Фаза
**необратима** для этого source/model job. После неожиданной
ошибки сборки или гибели процесса оставшиеся source-atom ответы
повторно валидируются **строго без сетевых запросов**. Пропавшая
проверенная запись, изменение исходника/модели или расхождение
identity приводят к отказу, а не повторной оплате Gemini.
Вторая отдельная квота — максимум **3 локальных неудачи**
finalization, включая истечение lease; это не бесконечный retry.

При terminal completed/failed/cancelled существующий SQLite
trigger стирает оригинальные raw checkpoint и новый recovery
manifest в одной транзакции. Нет содержимого книг, промптов или
ключа в recovery metadata.

Это перенос **debt-wave + finalize-only поведения**.
Рекурсивные `split_v2` с деревьями leaf-тасков, полноценная
отдельная desktop `translation_debts` queue и fallback-политика
модели остаются **отдельной** приёмкой; не считать весь настольный
recovery портированным.

Offline tests: 14 доменов, 13 долгов, 12 repair-запросов в первый
проход, 1 оставшийся во второй без повторения 13 готовых;
обрыв после атомной записи finalize-only и восстановление
при `max_attempts=1` без нового API; пропажа checkpoint,
смена source/model/lease — fail closed; три повторных сбоя
сборки завершают задачу и очищают приватные копии.
