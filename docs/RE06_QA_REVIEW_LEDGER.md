# RE-06 — постоянные терминологические QA-отчёты и решения модераторов

Источник проверяющих правил: перенесённый desktop `translation_gates.py` (PR #47), не
новая текстовая эвристика или Gemini-проверка. Данные доступны только авторизованным
участникам команды, как и существующие редакторские заметки. В продукте две роли:
администратор и модераторы; у книги есть переназначаемый владелец-модератор.
Пока принятая архитектура редактора допускает совместную работу модераторов.

## Хранимый контракт

Таблица `chapter_qa_reports` связана с конкретной книгой/главой, содержит
неизменяемую комбинацию source revision/hash, accepted revision/SHA256 и
glossary revision/SHA256, версию правил, дату, автора запуска и точное число
findings. Исторические отчёты не удаляются при появлении нового текста.

`chapter_qa_findings` хранит desktop code, severity, признак *would_block*,
machine-readable evidence и текущее решение `open/reviewed/waived`.
`chapter_qa_review_events` — дополняемый журнал изменений статусов
с actor, временем, прежним статусом, новой ревизией и причиной.
Допуск `waived` без письменной причины запрещён.
Две параллельные правки одного finding контролируются CAS review revision.

GET /v1/books/{book_id}/chapters/{chapter_id}/qa
возвращает только отчёт по **актуальным** source/accepted/glossary ревизиям.
POST /qa с ожидаемыми тремя ревизиями запускает только локальный
`run_translation_gates`, затем повторно проверяет все исходные fingerprint
в SQLite BEGIN IMMEDIATE. Повторение сканирования той же ревизии
возвращает исходный отчёт, не сбрасывая reviewed/waived.
PATCH /qa/findings/{finding_id} требует expected_review_revision и
expected_source/accepted/glossary_revision. Недействительная/чужая
ревизия → 409/404, без переиспользования старого решения.

## Важная граница достоверности

Для **вручную принятого** перевода SQLite не хранит доказательство полного
атомного выравнивания target-slot с source-slot. Поэтому при повторном
сканировании accepted вызывается desktop gate **только с
alignment_proven=False**, даже если в прошлом автоматическое задание
прошло CoverageMap. Автоматическое присвоение proof по количеству HTML
элементов запрещено. Машинные кодовые findings и даже desktop
blocking=True — **диагностика**, ни один статус в данном PR не запрещает
публикацию, не перезаписывает accepted_html и не инициирует Gemini.
Для строго доказанного positional QA нужен отдельный сохранённый
атомный provenance по текущей accepted revision.

Оригинал, перевод и доказательства могут присутствовать в защищённом
QA-отчёте, но **не** копируются в глобальные job events/логи:
автоматические события содержат лишь код, severity и ID слота.
В UI текст/свидетельства вставляются только через textContent;
клиентские ключи не записываются в localStorage/sessionStorage.

Сканирование ограничено первыми 64 находками; фактическое количество
и признак `truncated` записываются отдельно. Для evidence одного
finding действует лимит 16 KiB. Это read-only редакторская диагностика,
не массовый экспорт приватных материалов.

## Испытания и дальнейшая приёмка

`tests/test_chapter_qa.py`: HTTP 401 и авторизация модераторов,
persist после перезапуска SQLite, точные source/accepted/glossary revision
и fingerprint, history `waived` с причиной, CAS двух редакторов,
повторный scan без потери решений, source refresh/stale accepted,
новый accepted text и glossary invalidate report,
инъекция конкурентного принятия **между расчётом и записью**
должна дать 409, подмена accepted HTML без обновления revision
отклоняется по SHA, чужие ID изолированы.
`tests/browser/smoke.mjs`: принятие главы и read-only запуск панели
в Chromium без повторного Gemini.

Пока **не входит** в этот этап: просмотр всех исторических QA-отчётов
из редактора; бэкенд-привязка точного atom provenance после ручных
правок, автоматический строгий blocking, массовый corpus false-positive
аудит и повторные Gemini repair по лексике.
После гарантированной сохранности QA-решений следующий отдельный PR
должен доказать валидность source-owned positional evidence на корпусе
и только потом определить допустимые blocking-классы.

Конфигурация остаётся один API-ключ на один Google-проект,
без мультиключевой ротации, React и платных API-тестов.
