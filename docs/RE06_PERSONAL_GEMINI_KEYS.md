# RE-06 — Личные Gemini-ключи модераторов (RE-06-PERSONAL-01)

## Правило

**Один Google-проект — один Gemini API-ключ.** У каждого модератора может
быть несколько *разных* проектов; каждый из них привязан только к
зарегистрировавшему модератору. При повторном сохранении ключа существующего
проекта ключ заменяется, при попытке присвоить чужой проект — 409.
Повторно привязать один и тот же ключ к другому проекту нельзя.

При вводе модератор вручную указывает Google Cloud project ID. Сервис
сохраняет локально уникальность идентификатора и fingerprint ключа, но
**не проверяет, действительно ли Google выдал этот ключ именно данному
project ID**. Никаких платных запросов или проверки квот при сохранении.
Не считайте ввод второго ID реальным способом получить независимую квоту.

## Браузер

`/app/cabinet` → «Мои ключи Gemini». Поля: ID проекта, API-ключ. Кнопки
«Сохранить ключ» и «Удалить»; вместо сохранённого секрета отображается
только ID проекта. Не показываем и не возвращаем ключ после сохранения.
UI очищает поле password до завершения запроса и при выходе со страницы,
ничего не хранит в `localStorage`/`sessionStorage`.

`GET /v1/me/gemini-keys` — проекты только текущего участника;
`POST /v1/me/gemini-keys` — создать/заменить; `DELETE
/v1/me/gemini-keys/{project_id}` — удалить свой проект. Cookie-сессия
HttpOnly/Secure/SameSite=Strict, CSRF на изменение, no-store на ответы.
Администратор не может прочитать чужой Gemini-ключ через API.

## Шифрование и включение на сервере

Реальная база SQLite хранит `nonce`, AES-256-GCM `encrypted_key`, HMAC
fingerprint, member ID и указанный project ID. Не содержит plaintext
Gemini API-ключа. В шифрование включены member/project как authenticated
AAD: перенос чужого ciphertext к другому модератору/проекту отвергается.
Секрет мастер-ключа (32 байта, base64) **не хранится в SQLite**.
Его выдаёт оператор через защищённый systemd `LoadCredential` с
именем `gemini_vault_key` или через `CHAPTERA_GEMINI_VAULT_KEY` для
локальных тестов; тот же неизменный секрет должен быть доступен И API,
И worker. Не печатайте значение в Actions/CLI/логи и не используйте
репозиторий как secret store. При утрате мастер-ключа ранее сохранённые
ключи нельзя расшифровать; перед его ротацией нужен отдельный безопасный
план миграции. В момент отсутствия мастер-ключа UI показывает
«хранилище не настроено», POST/DELETE отвечают 503.

**Важная граница запуска:** если мастер-ключ вообще не настроен, старый
worker остаётся на защищённом системном `CHAPTERA_GEMINI_API_KEY`; это
нужно для обратной совместимости с первичным VPS bootstrap. Как только
оператор настроит vault key у обоих сервисов и перезапустит их,
worker использует **только ключи модераторов** и не переключается
молча на общий host key. Смешанные версии API/worker недопустимы.
Без личного ключа задание остаётся в SQLite без платной попытки.

## Выполнение и квоты

Один существующий worker выбирает провайдера по `actor_id` задания.
Ключи других участников не используются. Для нескольких собственных
проектов применяется простой круговой выбор между главами. Для каждого
проекта сохраняется отдельный RPM/TPM scheduler, а при настроенном
`gemini_requests_per_day` — отдельный SQLite ledger
`(project, model, Pacific day)` с существующей desktop-логикой ошибок
и checkpoint. Параллельных Gemini-запросов не добавлено.

Отзыв или замена ключа проверяется **перед каждым последующим
Gemini-вызовом** текущей главы; иной модератор не страдает от отзыва
ключа соседа. Если ключ был удалён между резервированием задания и
выбором проекта, задача переходит в ожидание без потери retry budget.
Уже отправленный сетевой запрос невозможно отменить ретроспективно.

## Тесты и границы

`tests/test_personal_gemini_keys.py` проверяет сохранение ciphertext,
CSRF и чужие полномочия, дубликаты project/key, замену/отзыв,
разные ключи при работе worker и сохранение очереди при отсутствии ключа.
`tests/browser/smoke.mjs` проверяет реальный личный кабинет,
добавление ключа и его отсутствие после удаления/перезагрузки.

Нет автоматического обмена чужими ключами, «дожигания» остатков,
наблюдения активности, нового диспетчера или real Gemini оплаты.
Запуск на VPS потребует отдельного операторского добавления защищённого
мастер-ключа к systemd-юнитам (только после root bootstrap #46).
Не раскрывайте ключ шифрования в репозитории, Notion или логах CI.
